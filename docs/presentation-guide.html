1. The Big Picture

What is Playwright?

Playwright is a tool that controls a real web browser (Chrome, Firefox, Safari) through code. Instead of a person clicking buttons and typing text, your TypeScript code does it automatically. Think of it like a robot sitting at your computer, clicking exactly where you tell it to, typing what you say, and checking if the page shows the right thing.

Why not just test manually?

Imagine you have a shopping website. Every time a developer changes something, someone has to: register a new user, log in, search products, add to cart, checkout, pay, verify the invoice... across 3 browsers. That's hours of clicking every single time. Playwright does it all in under 2 minutes.

Why Playwright over Selenium?

FeatureSeleniumPlaywright
Waiting for elementsYou write explicit waitsAuto-waits for you
SpeedHTTP protocol (slower)Direct browser protocol (faster)
BrowsersNeeds separate driversAll 3 built in
Network mockingNeeds extra toolsBuilt in
Trace debuggingNothing comparableFull timeline replay
Visual testingThird-party librariesBuilt in

What is a test automation framework?

Analogy: Think of a restaurant kitchen. You don't just have a chef cooking randomly. You have:

  • Recipes (test cases) — what to cook
  • Ingredients storage (test data) — organized in the pantry
  • Standard tools (page objects) — same knife for every chef
  • Quality checks (assertions) — taste before serving
  • Kitchen layout (folder structure) — everyone knows where things are

A framework is the organized kitchen that makes cooking (testing) fast, consistent, and repeatable.

The Problem Statement (5 Lines)

  1. Our client runs an online retail platform with critical customer journeys (register, shop, pay).
  2. Testing these flows manually across 3 browsers takes hours and misses bugs.
  3. They need automated tests that run reliably every time code changes.
  4. The framework must be maintainable so new team members can add tests easily.
  5. It must also cover accessibility, visual consistency, and produce clear reports for stakeholders.

4. Key Concepts

Page Object Model (POM)

Analogy: Think of a TV remote. You press "Volume Up" — you don't care which circuit board signal fires. The remote is the page object. The circuit board is the HTML.

// login.page.ts - The "remote control" for the login page
export class LoginPage extends BasePage {
  private readonly loginEmail: Locator;     // The email button on the remote
  private readonly loginPassword: Locator;  // The password button
  private readonly loginButton: Locator;    // The "go" button

  async login(email: string, password: string): Promise<void> {
    await this.loginEmail.fill(email);      // Press email, type value
    await this.loginPassword.fill(password);
    await this.loginButton.click();         // Press go
  }
}

Why: If the email field's HTML changes, you update login.page.ts once. Not every test.

Locator Strategy

Analogy: Finding a house. "The blue house on 5th street" (CSS selector) vs "House #42" (data-qa attribute). The house number never changes even if you repaint.

// Best: data-qa attributes (made for testing, never change)
page.locator('[data-qa="login-email"]')

// Good: semantic selectors (tied to function)
page.locator('a[href="/login"]')

// Last resort: text-based
page.locator('h2:has-text("Login to your account")')

Auto-Waiting (No Hard Sleeps)

Analogy: Imagine waiting for a bus. Selenium says "wait exactly 10 seconds" (you might wait too long or too short). Playwright says "wait until the bus arrives, up to 15 seconds." Smarter.

// BAD (Selenium-style): waits 3 seconds even if button appears instantly
await page.waitForTimeout(3000);
await page.click('#submit');

// GOOD (Playwright): waits only until the button is clickable
await page.locator('#submit').click(); // Auto-waits!

Custom Fixtures

Analogy: A hotel room service. You order "breakfast" and get everything prepared — you don't go to the kitchen yourself. Fixtures prepare page objects and hand them to your test.

// fixture sets up the page objects for you
export const test = base.extend<TestFixtures>({
  // Also blocks ads so tests don't get flaky
  page: async ({ page }, use) => {
    await page.route(/google|doubleclick|googlesyndication/, route => route.abort());
    await use(page);
  },
  loginPage: async ({ page }, use) => { await use(new LoginPage(page)); },
  homePage: async ({ page }, use) => { await use(new HomePage(page)); },
});

// In your test, just ask for what you need:
test('Login test', async ({ loginPage, homePage }) => {
  // loginPage and homePage are ready to use!
});

Data-Driven Testing

Analogy: A mail merge. Same letter template, different names and addresses. Same test logic, different data.

// testdata/products.json has: { "searchTerms": ["top", "tshirt", "dress", ...] }

for (const searchTerm of productData.searchTerms) {
  test(`Search for "${searchTerm}"`, async ({ productsPage }) => {
    await productsPage.searchProduct(searchTerm);
    // One test generated per search term. Add a term = add a test. No code change.
  });
}

Network Interception

Analogy: A mail filter. You can block spam (ads), redirect letters (mock responses), or slow down delivery (simulate slow network).

// Block all images to test page without them
await page.route('**/*.{png,jpg,gif}', route => route.abort());

// Simulate slow network (add 300ms delay to every request)
await page.route('**/*', async route => {
  await new Promise(r => setTimeout(r, 300));
  await route.continue();
});

Accessibility Testing (axe-core)

Analogy: A building inspector checks if a building has wheelchair ramps and braille signs. axe-core checks if your website works for people with disabilities.

const results = await new AxeBuilder({ page })
  .withTags(['wcag2a', 'wcag2aa'])  // Check against international standards
  .analyze();

// Filter for serious issues only
const critical = results.violations.filter(v =>
  v.impact === 'critical' || v.impact === 'serious'
);

Visual Regression Testing

Analogy: A "spot the difference" game. First run takes a photo (baseline). Every future run takes another photo and compares. If more than 5% of pixels changed, the test fails.

await expect(page).toHaveScreenshot('home-page.png', {
  maxDiffPixelRatio: 0.05,  // Allow 5% pixel difference
  fullPage: true,
});

Cross-Browser Execution

One command, three browsers. npm test runs all tests on Chrome, Firefox, and Safari. Use --project=chromium to target just one.

Reporting

  • HTML Report: Interactive dashboard with pass/fail, screenshots, traces. npm run report
  • JSON Report: Machine-readable for CI/CD pipelines.
  • Console (list): Real-time output while tests run.

AI-Assisted Test Creation

I used Claude Code (AI assistant) and the Playwright MCP server in VS Code to help generate test code. Here is how I used it responsibly:

  • AI generated the initial test structure and locators
  • I reviewed every line, ran the tests, and fixed issues
  • I understood what each line does before keeping it
  • AI helped speed up writing; the design decisions were mine

6. How It All Works Together

Tracing One Test from Start to Finish

Command: npx playwright test tests/user-login.spec.ts --project=chromium

  1. Config loaded: Playwright reads playwright.config.ts — gets baseURL, timeouts, browser settings
  2. Browser launched: Chromium starts (headless by default)
  3. Fixture runs: test-fixtures.ts creates a fresh browser page, blocks ad requests, creates HomePage and LoginPage objects
  4. Test data read: getLatestAccount() reads created-accounts.json for the latest credentials
  5. Page object actions: homePage.open() navigates to the site, loginPage.login(email, password) fills and submits the form
  6. Assertion: homePage.verifyLoggedIn(name) checks "Logged in as hariteja_..." is visible
  7. Cleanup: Browser closes, fixtures tear down
  8. Report generated: Results written to HTML report, JSON report, and console

Running Tests

# Run all tests (all browsers)
npm test

# Run one file, one browser
npx playwright test tests/user-login.spec.ts --project=chromium

# See the browser while it runs
npx playwright test tests/user-login.spec.ts --project=chromium --headed

# Step-through debugging (opens Inspector)
npx playwright test tests/user-login.spec.ts --project=chromium --debug

# Interactive UI mode (time-travel debugging)
npx playwright test --ui

Viewing Reports

# Open the HTML report (shows all test results)
npm run report

# Open a trace file (timeline replay of a failed test)
npx playwright show-trace test-results/<folder>/trace.zip

9. Interview Q&A (20 Questions)

1. Why did you choose Playwright over Selenium?

"Auto-waiting eliminates flaky explicit waits. Built-in network mocking, trace debugging, and visual regression mean fewer external tools. It's faster because it talks directly to the browser engine, not through an HTTP protocol."

2. What is the Page Object Model and why use it?

"Each page gets its own class that hides locators and exposes business actions. If a button's selector changes, I update one file, not every test that clicks it. Tests read like requirements: loginPage.login(email, password)."

3. How do you handle flaky tests?

"Three ways. First, Playwright's auto-wait handles timing issues. Second, I block ads at the network level because they overlay elements randomly. Third, I use retries in config (1 retry locally, 2 in CI), and traces are captured on retry to debug the root cause."

4. How do you handle waits in Playwright?

"I don't use hard sleeps. Playwright auto-waits for elements to be visible, enabled, and stable before acting. For assertions, expect() retries until the condition is met or timeout expires. The only explicit waits I use are waitFor() for modals or navigation."

5. What's the difference between fixtures and beforeEach?

"Fixtures are lazy — they only create what a test requests. A test that needs only contactUsPage doesn't pay the cost of constructing checkoutPage. They also support dependency injection, type safety, and automatic teardown."

6. How do you handle test data?

"Test data lives in JSON files under testdata/. A typed utility reads them. For unique data like emails, I generate timestamps at runtime. Credentials from registration tests are saved to a JSON file that login tests read."

7. How do you handle cross-browser testing?

"playwright.config.ts defines three browser projects: Chromium, Firefox, and WebKit. npm test runs all tests on all three. I can target one browser with --project=chromium. Visual tests only run on Chromium because pixel-level baselines differ across browsers."

8. What is network interception and when would you use it?

"page.route() intercepts HTTP requests. I use it to block ads for test stability, simulate slow networks, mock API responses for edge cases, and capture/validate response status codes."

9. How does your accessibility testing work?

"I use axe-core, the industry-standard engine. It scans the rendered page against WCAG 2.0 Level A and AA rules. I filter for critical and serious violations. Each failure includes the rule ID, description, and a URL explaining how to fix it."

10. How does visual regression testing work?

"First run creates baseline screenshots. Subsequent runs compare against those baselines. If more than 5% of pixels differ, the test fails. I update baselines with --update-snapshots when intentional UI changes happen."

11. How would you integrate this with CI/CD?

"The framework already outputs JSON reports for machine parsing. In GitHub Actions or Jenkins, I'd run npm test, publish the HTML report as an artifact, and fail the pipeline if any test fails. The config already has CI-specific settings for retries and workers."

12. How do you debug a failed test?

"Four levels. First: check the HTML report for the failure screenshot. Second: open the trace file — it shows a timeline of every action with DOM snapshots. Third: run with --headed to watch it live. Fourth: run with --debug for step-by-step execution with the Inspector."

13. Why TypeScript over JavaScript?

"Compile-time error detection catches mistakes before tests run. IDE autocomplete shows what methods a page object has. Interfaces like RegistrationData serve as living documentation. Renaming a method flags every broken caller immediately."

14. How do you make tests independent of each other?

"Each test gets a fresh browser context — no shared cookies or state. Registration tests generate unique emails with timestamps. Tests that need an existing account read from a saved credentials file rather than depending on test execution order."

15. What's your locator strategy?

"I prioritize data-qa attributes because they exist solely for testing and are stable. Second choice: semantic selectors like a[href='/login']. Last resort: text-based selectors. I avoid fragile XPath or deeply nested CSS selectors."

16. How would you scale this for a larger application?

"The structure already scales: add a page object for each new page, register it in fixtures, write tests. For a very large suite, I'd add test tagging (@smoke, @regression), parallel execution sharding, and possibly API-level setup to skip UI steps where possible."

17. How did you use AI in building this?

"I used Claude Code to help generate test structures, locators, and boilerplate. Every line was reviewed and tested by me. AI accelerated the writing; the architecture decisions, debugging, and quality assurance were mine. I'm transparent about this because responsible AI usage is a modern engineering practice."

18. Why did you block ads in the fixture?

"automationexercise.com loads Google Ads that overlay clickable elements and appear inconsistently. Blocking at the network level with page.route() is more reliable than trying to close popups, and it makes tests faster and deterministic."

19. What would you improve if you had more time?

"CI/CD pipeline integration with GitHub Actions, API-level testing for backend validation, mobile viewport testing, performance benchmarking, and possibly a custom reporter for Slack notifications."

20. What if you don't know the answer to a question?

Say: "That's a great question. I haven't worked with that specifically yet, but based on what I know about [related concept], I'd approach it by [logical next step]. I'd want to research it further before implementing." Honesty builds more trust than a wrong answer.

10. Tips for Tonight

1. Run the full suite and open the HTML report. 
npx playwright test --project=chromium
npm run report
Have the report open and ready to show during the demo.
2. Make a test fail on purpose. Change an assertion (e.g., verify wrong text), run it, then open the trace: 
npx playwright show-trace test-results/<folder>/trace.zip
Panels love seeing you debug confidently.
3. Memorize these two answers:
  • "Why this locator?" → "data-qa attributes are stable and exist only for testing."
  • "How do you handle waits?" → "Playwright auto-waits. I never use hard sleeps."
4. Be honest about AI usage. "AI helped me write faster. I reviewed every line, ran every test, and made every design decision myself." That's exactly what they want to hear.
Weak spots to be ready for:
  • Your new tests (user-registration, user-login, etc.) use the same account via a JSON file. If asked about test isolation, explain the trade-off: convenience vs. full independence. In a production framework, you'd use API calls to create/delete accounts per test.
  • The Polo brand page shows "Blue Top" and "Fancy Green Top" which aren't actually Polo T-shirts. If asked, explain: "The test validates the cart flow, not the product filtering logic on the server side."
