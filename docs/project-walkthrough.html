Phase 4: Packages Installed — What and Why

PackageTypeWhat It DoesWhy We Need It
@playwright/test Dev The Playwright test runner, assertion library, and browser automation engine Core requirement of the capstone. Provides test(), expect(), page objects, and all browser control.
@axe-core/playwright Prod Accessibility testing engine that scans pages for WCAG violations PDF requires "Accessibility Testing using axe-core". This runs the axe engine inside Playwright's browser context.
dotenv Prod Loads environment variables from a .env file into process.env Lets us configure BASE_URL per environment (dev/staging/prod) without changing code. CI systems set env vars natively.
@types/node Dev TypeScript type definitions for Node.js built-in modules (fs, path, etc.) Our utilities use fs.readFileSync and path.resolve. Without this, TypeScript can't type-check those calls.
Why only 4 packages? Playwright bundles its own test runner, assertion library, reporters, and screenshot comparison. We don't need Mocha, Chai, Jest, Allure, or any other testing library. Fewer dependencies = fewer security vulnerabilities, faster installs, and less maintenance.

Phase 5: Page Objects — The Core Architecture

What is the Page Object Model?

POM is a design pattern where each page of the web application has a corresponding class in the code. The class contains all the locators (how to find elements) and actions (what you can do on the page). Tests never touch raw locators — they call page object methods instead.

base.page.ts — The Parent Class

pages/base.page.ts
Defines shared methods that every page needs: navigate(), getTitle(), waitForPageLoad(), takeScreenshot(), getText(). Every other page extends this class.
Why: Without a base class, every page object would duplicate these 5 methods. With 8 page objects, that's 40 duplicate methods eliminated.

Locator Strategy

Every locator was chosen in this priority order:

PriorityStrategyExampleWhy
1stdata-qa attributes[data-qa="login-email"]Most stable. Explicitly placed for testing. Won't change with UI redesigns.
2ndSemantic HTML attributesa[href="/login"]Tied to functionality, not appearance. Rarely changes.
3rdID selectors#search_productUnique per page. Stable but less common than data-qa.
4thText-based selectorsh2:has-text("Login")Last resort. Readable but breaks if text changes.

Phase 6: Fixtures — Dependency Injection

fixtures/test-fixtures.ts
Extends Playwright's built-in test object with custom fixtures that automatically construct and inject page objects into every test.

What This File Does

Instead of tests creating page objects manually:

// WITHOUT fixtures (bad - repetitive)
test('login', async ({ page }) => {
  const loginPage = new LoginPage(page);
  const homePage = new HomePage(page);
  // ... use them
});

Tests declare what they need and the fixture provides it:

// WITH fixtures (good - clean)
test('login', async ({ loginPage, homePage }) => {
  // loginPage and homePage are ready to use
});

Ad Blocking

The fixture overrides Playwright's default page fixture to intercept and abort ad network requests:

page: async ({ page }, use) => {
  await page.route(
    /google|facebook|doubleclick|googlesyndication|adservice/,
    route => route.abort()
  );
  await use(page);
},
Why: automationexercise.com loads Google Ads that overlay clickable elements and cause random test failures. Blocking at the network level is 100% reliable, unlike trying to close popup ads (which appear inconsistently).

Phase 7: Test Suites — All 8 Files Explained

1. auth.spec.ts — User Authentication (3 tests)

tests/auth.spec.ts
Tests registration, login/logout, and invalid login error handling.
TestWhat It Verifies
Register new user, verify, deleteFull registration flow: enter name/email, fill form, submit, verify "Account Created" message, delete account for cleanup
Login with valid credentials and logoutRegisters first (so credentials exist), logs out, logs back in with those credentials, verifies "Logged in as" text, logs out again
Invalid credentials shows errorAttempts login with wrong email/password, verifies error message appears
Why unique emails per test? Each test generates register_1697234567890@test.com using Date.now(). This prevents "Email already exists" errors and lets tests run in parallel without conflicts.

2. product-search.spec.ts — Data-Driven Search (7 tests)

tests/product-search.spec.ts
Runs the same search test for 5 different terms from testdata/products.json, plus product detail and listing tests.
// This loop generates 5 separate tests from one block of code
for (const searchTerm of productData.searchTerms) {
  test(`Search for "${searchTerm}"`, async ({ productsPage }) => {
    // Same logic, different data each time
  });
}
Why data-driven? Adding a new search term means editing products.json, not writing new TypeScript. Separates test logic from test data.

3. cart.spec.ts — Shopping Cart (4 tests)

tests/cart.spec.ts
Add multiple products, remove items, verify quantities and details, test quantity from product detail page.

4. checkout.spec.ts — End-to-End Purchase (1 long test)

tests/checkout.spec.ts
The most comprehensive test: register → add products → checkout → verify address → place order → fill payment → confirm → cleanup.
Why one long test instead of many small ones? Checkout is a single user journey. Breaking it into separate tests would require sharing state between them (logged-in session, cart contents), which violates test isolation. One test = one complete business flow.

5. contact-us.spec.ts — Contact Form (2 tests)

tests/contact-us.spec.ts
Fill all form fields, upload a file, handle the browser confirm dialog, verify success message.
Interesting detail: The site shows a browser confirm() dialog on form submit. The test handles it with page.once('dialog', dialog => dialog.accept()) — registering a one-time listener before clicking submit.

6. accessibility.spec.ts — axe-core WCAG (3 tests)

tests/accessibility.spec.ts
Scans Home, Login, and Products pages for WCAG 2.0 Level A/AA violations using axe-core.
const results = await new AxeBuilder({ page })
  .withTags(['wcag2a', 'wcag2aa'])
  .analyze();
Why filter for critical/serious only? axe-core reports 4 severity levels (minor, moderate, serious, critical). Failing on every minor issue would make tests too noisy. Critical and serious violations are the ones that prevent users with disabilities from using the site.

7. visual.spec.ts — Visual Regression (3 tests)

tests/visual.spec.ts
Takes full-page screenshots and compares against stored baselines. Fails if pixels differ by more than 5%.
await expect(page).toHaveScreenshot('home-page.png', {
  maxDiffPixelRatio: 0.05,
  fullPage: true,
});
Why Chromium only? Different browsers render fonts and layouts differently. Maintaining separate baselines per browser triples maintenance without proportional value. Functional cross-browser coverage comes from the other test files.

8. network-mock.spec.ts — Network Interception (5 tests)

tests/network-mock.spec.ts
Demonstrates intercepting requests, mocking, blocking images, simulating slow networks, and capturing response status codes.

Phase 9: Configuration Files

playwright.config.ts

SettingValueWhy
fullyParalleltrueTests run concurrently for faster execution. Each test gets its own browser context, so there's no shared state.
retries1 local, 2 in CIWeb tests can be flaky due to network timing. Retries catch transient failures without masking real bugs.
workersauto local, 1 in CILocal: use all CPU cores. CI: single worker avoids resource contention on shared runners.
